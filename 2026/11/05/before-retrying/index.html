自动化失败后，为什么要先查结果再重跑

2026 · 11 · 05 · 3 min · Agent / Python / 开源

设想一条视频上传任务。服务端已经收到视频，客户端却在等待响应时超时。工作流显示失败，平台上可能已有这条视频。如果看到红叉就再传一遍，故障可能变成重复发布。博客也有类似情况：文章已提交，但后续部署仍可能失败。

报告先交代已经确认的事

工作流的结论描述执行过程。文章是否已上线、视频是否已进入平台后台，要去目标端核对。故障报告应把两种状态分开写：一次运行因超时结束是已知事实，发布结果待确认是接手人下一步要查的问题。

从故障报告借鉴复现方式

一份报告可以把运行链接、尝试次数、症状和下一步放在一起。权限错误就核对令牌与目标仓库，网络超时则先查目标端有没有接收内容。日志暂时拿不到时，可以留下“证据不足”，让后续的人知道哪些判断还需要补证据。

我希望无人值守任务在出问题时也能把现场交代清楚。这样的报告也方便向维护者反馈：先描述实际影响，再附可复现的线索。博客发布场景的实现和演练已经公开。查看 Auto Blog Agent。
